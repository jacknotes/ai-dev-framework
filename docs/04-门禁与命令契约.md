# 门禁与命令契约规范

> 版本：v1.0　｜　定位：`docs/01`（宪法）与 `docs/03`（方案）的**执行层规范**
> 解决的问题：把"门禁"从一句口号，变成**能被机器判定的退出码**。

---

## 1. 为什么需要这一层

`pipeline/pipeline.workflow.js` 里最早的 `gatePass()` 是这样的：

```js
function gatePass(stage, detail) {
  log(`[门禁] ${stage}: ${detail}`);
  return true; // 永远通过
}
```

**这等于没有门禁。** 任何失败都会被"通过"，整套框架退化成角色扮演——这是框架从"文档"变成"能用的东西"之间唯一真正的鸿沟。

修复的关键认知有两条：

1. **门禁必须由真实命令的退出码决定**，而不是由某个智能体"觉得通过了"决定。
2. **编排器不应该知道你用 npm 还是 go test**。它只认一套固定的命令入口。

这就是"命令契约"（command contract）。

---

## 2. 五入口契约

每个项目根目录必须有 `scripts/`，且**恰好**提供这 5 个入口：

| 入口 | 用途 | 通过条件 | 失败时 |
|---|---|---|---|
| `scripts/lint.sh` | 静态检查 / 格式 | `exit 0` | `exit ≠ 0` |
| `scripts/build.sh` | 构建产物 | `exit 0` 且产物存在 | `exit ≠ 0` |
| `scripts/test.sh` | 单元测试 + 覆盖率 | `exit 0`（覆盖率阈值内置在脚本里） | `exit ≠ 0` |
| `scripts/health.sh` | 部署后健康检查 | `exit 0` | `exit ≠ 0` |
| `scripts/e2e.sh` | 集成 / UI 测试（隔离环境内） | `exit 0` | `exit ≠ 0` |

### 硬性约束

1. **必须幂等**：连续跑两次结果一致（不累积状态）。
2. **不依赖交互**：不得等待 stdin 输入。
3. **失败要有可读原因**：末行输出能直接贴进失败报告。
4. **不得吞掉退出码**：禁止 `cmd || true`、`cmd; exit 0` 这类写法。
5. **不联网安装依赖**：依赖应在 `setup` 阶段装好（CI 里是 `npm ci` / `pip install`）。
6. **只读业务代码**：脚本本身不得修改源码。

### 为什么是 5 个而不是更多

`lint/build/test` 对应编码门禁的三个维度，`health` 对应部署门禁，`e2e` 对应验收门禁。再细的划分（比如把安全扫描也做成入口）会让编排器耦合到具体工具，反而失去可插拔性。

安全扫描与性能测试**不进五入口**——它们是独立智能体的职责，输出去 `docs/test/`，判定标准是"0 Critical/High"和"指标达标"，由对应智能体按 `prompts/06`、`prompts/05` 自行执行并给出结构化结论。

## 3. 三道门禁的判定链

```
┌─ scripts/lint.sh  ─┐
├─ scripts/build.sh ─┼─→ 编码门禁  → 不过则退回编码
└─ scripts/test.sh  ─┘

scripts/e2e.sh ─────────→ 验收门禁  → 不过则退回开发

scripts/health.sh ──────→ 部署门禁  → 不过则回滚
```

编排器对每道门禁的执行逻辑是统一的：

```
最多重试 N 次（默认 3）
  ├─ 运行脚本
  ├─ exit 0        → 门禁通过，进入下一阶段
  └─ exit ≠ 0      → 携带失败输出退回上一环节，重跑
重试耗尽仍失败       → 暂停，人工介入
```

## 4. 编排器如何"真实执行"脚本

有一个容易被忽略的实现约束：**DSH workflow 脚本本身没有文件系统与进程权限**（它只有 `agent()` / `parallel()` / `phase()` / `log()` / `args`）。

所以门禁不能这样写：

```js
// ✗ 错误：workflow 脚本里跑不了 shell
const code = execSync('./scripts/lint.sh');
```

**正确做法**：让一个"门禁执行智能体"去跑，并返回**结构化结果**。编排器只信这个结构化的 `passed` 字段：

```js
const gate = await agent(`在项目根目录执行 bash scripts/lint.sh，如实回报退出码…`, {
  schema: {
    type: "object",
    properties: {
      passed:   { type: "boolean" },
      exitCode: { type: "number"  },
      summary:  { type: "string"  },
      failures: { type: "array", items: { type: "string" } },
    },
    required: ["passed", "exitCode", "summary", "failures"],
    additionalProperties: false,
  },
});
```

这样做的两个好处：

- **门禁不可伪造**：智能体拿到的是真实退出码，`passed` 由 `exitCode === 0` 推出，不是它"感觉"。
- **失败可归因**：`failures` 数组直接进退回报告，开发智能体拿到的是可执行的修复清单。

> 这条设计也解释了为什么"门禁不可跳过"必须靠架构而非靠提示词——编排器**没有能力**绕过脚本去宣布通过。

## 5. 各技术栈的入口实现参考

| 栈 | lint | build | test |
|---|---|---|---|
| React/Vue + Vite | `npm run lint` | `npm run build` | `npm test` |
| FastAPI | `ruff check .` | `python -m compileall app` | `pytest --cov` |
| Go | `go vet ./...` | `go build ./...` | `go test ./... -cover` |
| Java/Maven | `mvn -B checkstyle:check` | `mvn -B package -DskipTests` | `mvn -B test` |
| .NET | `dotnet format --verify-no-changes` | `dotnet build -c Release` | `dotnet test` |
| JSP/Servlet | `mvn -B checkstyle:check` | `mvn -B package -DskipTests` | `mvn -B test` |

**新增一个技术栈时，只需实现这 5 个脚本。** 编排器、CI、所有验收角色零改动——这就是 `docs/03` §2.3 说的"技术栈可插拔"的工程落地。

## 6. 与 CI 的关系

`.github/workflows/ai-dev-pipeline.yml` 里每个 job 都调同一批脚本，避免"本地门禁"与"CI 门禁"两套口径：

```yaml
- run: bash scripts/lint.sh
- run: bash scripts/build.sh
- run: bash scripts/test.sh
```

**同一份契约，本地能过、CI 就能过**——这是减少"改了本地却红在 CI"这类返工的根本办法。

## 7. 自检清单（新增项目/模板时逐条打勾）

- [ ] `scripts/` 下 5 个文件齐全且可执行
- [ ] 每个脚本首行是 `#!/usr/bin/env bash`
- [ ] 每个脚本有 `set -euo pipefail`
- [ ] 工具未安装时，脚本给出**明确提示**并以非 0 退出（不能静默通过）
- [ ] 连续跑两次结果一致
- [ ] 失败输出末行可直接作为失败原因
- [ ] 编排器脚本里没有硬编码任何具体工具命令

## 8. 实测验证记录（本机，无 Docker）

为了证明这套契约**真的能判定**而不是纸面设计，做了两组实测：

### 8.1 正向：五道门禁全部通过

```
编码-静态检查  scripts/lint.sh     exit=0  通过
编码-构建      scripts/build.sh    exit=0  通过
编码-单元测试  scripts/test.sh     exit=0  通过
验收-e2e       scripts/e2e.sh      exit=0  通过
部署-健康检查  scripts/health.sh   exit=0  通过
```

### 8.2 负向：门禁必须能"红"

在 `backend/app/routers/greeting.py` 末尾故意注入一段语法错误：

```python
def broken(:
    pass
```

结果：

```
编码-静态检查  exit=1  失败   [lint] 失败：存在未通过的静态检查项
编码-构建      exit=1  失败   [build] 失败：存在未通过的构建项
编码-单元测试  exit=1  失败   [test] 失败：存在未通过的单元测试
→ [verify] 有 3 项失败，整体 exit=1
```

还原代码后立即恢复全绿。

> **这一组负向测试比正向更重要**：它证明门禁不是摆设。
> 如果注入错误后仍然全绿，说明门禁恒真——那就退化成了角色扮演。

### 8.3 实测中修复的两个真实缺陷

| 缺陷 | 现象 | 根因 | 修复 |
|---|---|---|---|
| 模板测试门禁开箱即红 | `coverage for functions (66.66%) does not meet 80%` | 覆盖率统计把 `main.tsx`、`dist/` 等无业务逻辑文件算进去了 | `vite.config.ts` 的 `coverage.exclude` 显式排除入口/声明/测试/构建产物 |
| 钉死版本装不上 | `pydantic==2.9.2` 在 Python 3.14 上源码编译失败 | 该版本无 3.14 预编译 wheel，被迫编译 `pydantic-core` | 改用兼容区间 `>=x,<y`；需要可复现时另生成 `requirements.lock.txt` |

> 这两个缺陷都是**"跑一遍才能发现"**的：文档看起来都对，实际执行才知道门禁是红的。
