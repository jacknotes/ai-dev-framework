# AI 全闭环开发落地方案

> 版本：v1.0　｜　定位：`docs/01-开发规范文档.md`（宪法）的**实施解释篇**
> 本文回答四个"我不明白"：①一个会话还是多会话　②测试交给谁　③运维交给谁　④安全交给谁
> 并给出「编程 → 测试 → 部署 → 交付」的完整闭环与**纯隔离测试环境**的落地方案。

---

## 0. 一页结论（TL;DR）

| 你的疑问 | 结论 | 一句话理由 |
|---|---|---|
| 一个大模型多会话，还是单会话全管？ | **多智能体（多会话/多 subagent）+ 一个编排器** | 独立性来自"上下文与工具隔离"，不是靠提示词自称独立 |
| 前端细分 JSP/React，后端细分 Go/Python/Java/.NET，要不要每个栈一个 AI？ | **角色稳定、技术栈可插拔**——不为每个栈新建角色，为每个栈准备一份"技术栈画像" | 角色管职责，栈管命令；否则角色数会随 `前端栈 × 后端栈` 组合爆炸 |
| 测试谁做？ | **单元测试开发自己写；集成/功能/UI/兼容/性能由独立测试 AI 做** | 自己判自己等于没判；但单测贴着代码写才划算 |
| 运维谁做？ | **部署脚本由开发/架构提供给仓库，执行部署与 runbook 由独立运维 AI 做** | 造的人和上线的人必须分开，否则"能跑"会被当成"能上线" |
| 安全谁做？ | **独立红队 AI，且必须黑盒——不给它源码上下文** | 给了源码就是白盒测试，模拟不出真实攻击者 |
| 怎么不碰用户真实环境？ | **五重隔离 + 一次性环境 + 合成数据 + Mock + 用完即销毁 + 生产只读禁地** | 隔离靠基础设施强制，不靠提示词自觉 |

**一句话总纲：谁产出，谁就不验收；跨权限边界才切角色；同边界内切会话是为了并行，不是为了合规。**

## 1. 核心判断：一个会话，还是多个会话？

### 1.1 先看"单会话全管"会怎么坏

不是"效果差一点"，而是三重结构性失败：

| 失败点 | 机制 | 后果 |
|---|---|---|
| **上下文爆炸** | 需求 + 架构 + 前后端源码 + 测试日志 + 部署输出全塞进一条上下文，中后期必然超出窗口或严重稀释注意力 | 后期步骤质量断崖式下降，越到交付越糟 |
| **自我验收失效** | 同一个上下文里，模型已经"知道自己为什么这么写"，评审时会为既有实现找理由 | 四眼原则归零，缺陷直接流入生产 |
| **不可并行 / 不可审计** | 单线程串行，且所有决策混在一段对话里 | 慢；出问题无法定位"哪一步、谁决定的"；无法回滚到中间状态 |

### 1.2 三种可行架构

| 方案 | 做法 | 隔离性 | 成本 | 适用 |
|---|---|---|---|---|
| **A. 单会话单角色** | 一次只让 AI 做一件事，人来回搬运上下文 | 强（天然隔离） | 人工介入频繁 | 手工小项目、教学演示 |
| **B. 多智能体 + 编排器**（本框架） | 编排器拆任务，按阶段调度独立 subagent，产物落 Git 交接 | **强**（subagent 独立上下文） | 中（token 与调度开销） | **推荐：符合你的目标** |
| **C. 单会话角色扮演** | 一个会话里"现在你是评审员、现在你是测试" | **弱，形同虚设** | 低 | 只适合快速演示，**不可用于验收** |

> C 的问题是根本性的：**角色扮演改的是措辞，不是上下文**。所谓"评审员"已经看过了开发者的全部推理过程和自我辩解，它只会复述"看起来是对的"。这不是评审，是自我确认。

### 1.3 关键认知：独立性是"架构属性"，不是"提示词属性"

```
✗ 错误做法：在同一个 context 里说「请以独立第三方视角审查上面的代码」
✓ 正确做法：开一个新的 subagent，只给它「代码 + 契约 + 需求」，不给它开发过程的思考
```

所以框架里 `prompts/04-reviewer.md` 写的是"你**只读代码**"——这句话必须由**工具权限**兜底（只给读工具，不给写工具），而不是只写在提示词里。这就是规范 §1 铁律三"最小权限靠工具/沙箱隔离实现，而非提示词口头约束"的真实含义。

### 1.4 但也别无脑切碎：切角色的三个必要条件

每引入一个智能体都有成本（token、时延、交接损耗）。满足**任一**条才值得切：

1. **权限边界不同**——一个能写代码、一个不能；一个能碰 staging、一个只能读。
2. **产物形态不同**——一个产出代码/PR，一个产出报告/环境/runbook。
3. **需要并行**——前后端同时开工，或有多个独立仓库。

三条都不满足 → **合并**。

据此的最小可行集：

| 角色 | 能否合并 | 说明 |
|---|---|---|
| 编排器 | 不可 | 它没有替代品 |
| PM | 可并入院线首发 | POC 期可由人类直接给需求 |
| 架构师 | 建议独立 | 契约是全局约束，混淆角色最容易产生歧义 |
| 前端 / 后端 | 可合 1 人（串行） | 但**不可与任何验收角色合并** |
| 代码评审 | **不可合并** | 必须独立上下文 |
| 测试 QA | **不可与开发合并** | POC 期可与安全合并为"质量智能体" |
| 安全红队 | **不可与开发合并** | **上线前必须与测试拆分**（黑盒要求） |
| DevOps | **不可与开发合并** | 生产发布前必须独立 |

> 阶段 2「任务拆解」虽然列在流水线里，但通常是编排器自己的活，**不必单开智能体**。交付汇总同理。

## 2. 角色与「技术栈」必须解耦

这是回答你"前端细分 JSP/React、后端细分 Go/Python/Java/.NET"的关键。

### 2.1 两个正交的维度

```
角色（Role）   = 职责边界   → 稳定，共 9 个，不随项目变
技术栈（Stack）= 命令与约定 → 可插拔，随项目选 1 个前端 + 1 个后端
```

如果按"JSP前端智能体""React前端智能体""Go后端智能体""Java后端智能体"去建角色，角色数 = `前端栈 × 后端栈`，组合爆炸，且每个都要单独写提示词与门禁——**不可维护**。

**正确做法**：一个"前端智能体"角色，运行时注入一份 **stack profile**（技术栈画像）：

```yaml
# 概念示例：stack profile 决定"怎么构建、怎么测、怎么跑"
stack: react-ts-vite
lint:  npm run lint
build: npm run build
test:  npm test          # 覆盖率门槛内置于脚本
run:   npm run dev
port:  3000
entry: frontend/
```

### 2.2 角色 × 技术栈矩阵

| 角色 | React | Vue | JSP/Thymeleaf | Go | Python | Java | .NET |
|---|---|---|---|---|---|---|---|
| 前端智能体 | ✅ 模板已备 | ✅ 模板已备 | ⚠️ 见 §2.4 | — | — | — | — |
| 后端智能体 | — | — | ⚠️ 见 §2.4 | ✅ | ✅ | ⚠️ 待补模板 | ⚠️ 待补模板 |
| 评审/测试/安全/运维 | 与栈无关，**同一套角色复用** | | | | | | |

> 注意最后一行：**验收类角色与技术栈无关**。测试 AI 不需要"懂 React"，它需要"会跑 `npm test`、会看报告、会对照验收标准"。这是框架能收敛到 9 个角色的根本原因。

### 2.3 统一命令契约（框架能自动化的前提）

编排器不应该知道"这个项目用 npm 还是 go test"。它只调用**固定 5 个入口**，由每个项目的 `scripts/` 实现：

```
scripts/lint.sh    # 门禁1：静态检查，exit≠0 即失败
scripts/build.sh   # 门禁2：构建，exit≠0 即失败
scripts/test.sh    # 门禁3：单元测试 + 覆盖率阈值
scripts/health.sh  # 门禁4：健康检查（部署后用）
scripts/e2e.sh     # 门禁5：集成/UI 测试（隔离环境内）
```

**好处**：新增 Java 模板时，只需实现这 5 个脚本，编排器、CI、所有验收角色**零改动**。这就是"技术栈可插拔"的工程落地。

### 2.4 JSP 这类遗留栈怎么处理

JSP 通常跑在 Tomcat/Servlet 容器里，**前后端边界天然是模糊的**（页面里嵌 Java 逻辑）。硬套"前端/后端两个智能体"会互相踩文件。三种处理方式，按优先级：

1. **按模块切，不按前后端切**——一个"应用智能体"负责 `web/WEB-INF/` 与 `.jsp`，另一个负责 `src/main/java/` 里的 service/DAO 层。边界是**目录**，不是"前端/后端"概念。
2. **契约仍然先行**——即使是 JSP，也先定 `api-spec.yaml`（Ajax 接口）与页面清单，两个智能体靠契约对齐，而非靠"我以为你会那样写"。
3. **不改技术栈就别追求自动化率**——JSP 项目通常缺少现代 lint/覆盖率工具，门禁只能做到"能编译 + 能启动 + 冒烟通过"。**接受这一点**，不要为了门禁去重构遗留系统。

### 2.5 什么时候才真的需要"再切一个智能体"

只有一种情况：**该技术栈需要一套互不兼容的工具链与知识**，且同时存在于一个项目里。典型例子：

- 单体仓库里同时有 React 前台 + Go 主服务 + Python 数据管道 → 切 3 个开发智能体（因为它们并行、目录不同、工具链不同）。
- 有 iOS 原生 + Android 原生 → 切 2 个。
- 只是"换个语言写后端" → **不切**，换 stack profile 即可。

## 3. 测试交给谁？——决策矩阵

**判断标准只有一条：这个测试的结论，能否被"写代码的人"自己判定为通过？**

| 测试类型 | 谁做 | 为什么 | 工具 |
|---|---|---|---|
| 单元测试 | **开发 AI 自己写** | 贴着代码写成本最低；但它验证的是"我写得对不对"，不是"需求满足没" | Vitest / pytest / go test / JUnit |
| 契约测试 | 独立测试 AI | 契约是前后端双方的约定，必须第三方裁判 | Schemathesis / Pact |
| 集成测试 | **独立测试 AI** | 跨模块协作，开发容易只测 happy path | pytest + Testcontainers |
| 功能/验收测试 | **独立测试 AI** | 严格对照 `requirements.md` 验收标准，开发自己判必然放水 | 用例矩阵 + Playwright |
| UI / E2E | **独立测试 AI** | 模拟真实用户操作，需要"不懂实现"的视角 | Playwright / Cypress |
| 兼容测试 | **独立测试 AI** | 浏览器/分辨率/OS 矩阵，纯执行型工作 | Playwright projects |
| 性能测试 | **独立测试 AI（或专职性能 AI）** | 需要压测环境与指标判定 | k6 / JMeter / locust |
| 安全测试 | **独立红队 AI（见 §5）** | 攻防视角，必须与建设方对立 | ZAP / nuclei / trivy |

**结论**：除单元测试外，**全部交给独立的测试 AI**。理由不是"它更专业"，而是**利益冲突**：让开发 AI 判定"我的功能是否通过验收"，等于让考生自己批卷。

三条硬性约束（必须由工具强制执行，不只是提示词）：

1. 测试 AI **无写权限**——不能改业务代码。
2. 测试 AI **不得修改测试用例让其变绿**——失败就是失败。
3. 测试只在**隔离 staging** 跑，绝不连生产库。

## 4. 运维交给谁？

**结论：拆成两半，一半归开发，一半归独立运维 AI。**

| 工作 | 归属 | 理由 |
|---|---|---|
| 写 Dockerfile / compose / K8s 清单 / Terraform | 开发 + 架构 | 这是代码的一部分，跟着业务演进 |
| **执行部署到 staging** | **独立运维 AI** | 部署是对"已完成产物"的操作，不是开发过程 |
| 健康检查、回滚、故障处置 | **独立运维 AI** | 需要"站在线上"的视角 |
| 写 `docs/runbook.md` | **独立运维 AI** | 可复用运维资产的沉淀者 |
| **发布生产** | **人类审批 + 运维 AI 执行** | 唯一不可自动化绕过的人为闸门 |

为什么不能让开发 AI 顺手部署？因为它会陷入 **"我部署成功了 = 我做对了"** 的循环：为了让自己这轮通过，它倾向于放宽探针、跳过迁移校验、把"健康检查失败"当成"环境问题"绕过。独立运维 AI 没有这个动机，它的 KPI 是"回滚干净、日志留全"。

**runbook 是硬交付物**，不是附带说明。判据：*任何一个新智能体（或新人）只读仓库，能否从零重建环境？* 不能，就是没交付。

## 5. 安全交给谁？——黑盒的关键是"不给源码"

**结论：独立红队 AI，且必须真正的黑盒。**

| 做法 | 效果 |
|---|---|
| 让开发 AI 自查安全 | ❌ 无效。它知道自己的后门、知道哪里有 TODO |
| 让测试 AI 顺便扫一遍（看源码） | ⚠️ 只算白盒审计，覆盖不到真实攻击面 |
| **独立红队 AI，只给 staging 地址，不给源码** | ✅ 等价于真实攻击者视角 |

核心机制：**上下文隔离 = 黑盒**。红队 AI 的输入只有：

```
- staging 的 URL
- 测试账号（低权限）
- OWASP Top 10 检查清单
```

**不给**：源码、设计文档、开发对话、内部接口说明、任何生产凭证。

它要覆盖的维度：Web 漏洞（SQLi/XSS/CSRF/SSRF/越权）、依赖与容器 CVE、认证授权与会话管理、异常输入与资源耗尽、限流与抗压。

同时必须约束：**只在隔离环境验证，不得对生产造成任何影响**；发现漏洞**不利用其扩大战果**，只出报告。门禁：**0 Critical / 0 High** 才放行。

## 6. 完整闭环：从需求到交付

### 6.1 状态机

```
        ┌──────────────── 门禁失败退回 ────────────────┐
        ↓                                              │
0 需求 → 1 架构 → 2 拆解 → 3 并行编码 → 4 评审 → 5 集成测试
                                                      ↓
                    10 交付 ← 9 验收(人类) ← 8 部署 ← 7 性能 ← 6 安全
```

### 6.2 阶段 · 负责 · 产物 · 门禁

| 阶段 | 负责智能体 | 产物 | 门禁（自动判定） |
|---|---|---|---|
| 0 需求澄清 | PM | `docs/requirements.md` | 每条功能有**可测**验收标准 |
| 1 架构设计 | 架构师 | `docs/architecture.md`、`docs/api-spec.yaml` | 契约可机器校验、覆盖全部需求 |
| 2 任务拆解 | 编排器 | Issue 列表 | 每个任务可独立验收 |
| 3 并行编码 | 前端 + 后端 | 代码 + 单测 | `lint` / `build` / 覆盖率 |
| 4 代码评审 | 评审 AI | `docs/review/*.md` | 0 Critical / 0 High |
| 5 集成测试 | 测试 AI | `docs/test/*-integration.md` | 用例 100% 通过 |
| 6 安全测试 | 红队 AI | `docs/test/*-security.md` | 0 Critical / 0 High |
| 7 性能测试 | 测试 AI | `docs/test/*-perf.md` | 延迟/吞吐达标 |
| 8 部署 staging | 运维 AI | 环境 + `docs/runbook.md` | 健康检查通过 |
| 9 验收 | 编排器 + 人类 | 交付报告 | **人类签字** |
| 10 交付 | 编排器 | Release + CHANGELOG | 交付物齐全 |

### 6.3 失败与回退（这是"极少人工干预"的关键）

| 情况 | 自动动作 | 升级条件 |
|---|---|---|
| 门禁不通过 | 携带**失败报告**退回上一环节重跑 | 重试 3 次仍失败 → 暂停等人 |
| 评审驳回 | 退回对应开发智能体，附问题清单 | 同一问题驳回 2 次 → 人看 |
| 部署失败 | 自动回滚上一稳定版本，保留现场日志 | 回滚也失败 → 立即告警 |
| 智能体跑偏 | 直接销毁重建，从 Git 当前状态继续 | — |

**"极少人工干预"不是靠 AI 更聪明，而是靠：①状态全在仓库（可随时重启）②失败自动退回（不需要人喊）③只在 3 个点找人（定目标 / 审批 / 验收）。**

## 7. 纯闭环测试环境：怎么确保不碰用户真实环境

### 7.1 五重隔离（缺一不可）

| 维度 | 要求 | 框架落地 |
|---|---|---|
| **环境隔离** | 一次性环境，从镜像 + IaC 全新建，用完即销毁 | `deploy/docker-compose.yml`，`up --build` → `down -v` |
| **网络隔离** | 独立网段，与生产内网不通 | `internal: true` + `172.30.0.0/24` |
| **凭证隔离** | 只用测试凭证，生产密钥**根本不注入** | `TEST_DB_PASSWORD=test_only_password`，CI 里无任何 secrets |
| **数据隔离** | 绝不连生产库，用合成数据 | Postgres 数据放 `tmpfs`，重启即清空，不落盘 |
| **执行沙箱** | 命令在受限容器内跑 | `read_only` + `no-new-privileges` + CPU/内存上限 |

### 7.2 数据策略（最容易被忽略的一条）

- **合成数据**：用 Faker 之类生成，结构真实、内容虚假。
- **黄金数据集**：固定一小份可复现的种子数据，保证测试结果稳定、可断言。
- **绝不脱敏真实数据**：脱敏是"可能漏"的，合成是"一定假"的。**测试环境里出现任何真实用户数据，视为重大违规。**

### 7.3 外部依赖：改成 Mock

支付、短信、第三方 API → WireMock 服务虚拟化（`deploy/mocks/wiremock-mappings.json`）。
好处：①不需真实凭证 ②可构造超时/500/重复回调等异常场景 ③测试可重复。

### 7.4 销毁与可复现

```bash
docker compose -f deploy/docker-compose.yml up -d --build   # 起
# ... 跑测试 ...
docker compose -f deploy/docker-compose.yml down -v          # 销毁，数据全清
```

**判据**：销毁后重新 `up`，环境必须与上次**完全一致**。不一致说明有状态泄漏（落盘、外部依赖、手工改动），必须修。

### 7.5 生产是"只读禁地"

- 所有自动化**只读**生产（监控、日志），**绝不写**。
- 生产发布：CI 里 `environment: production` + GitHub **Required reviewers**，人工点批准才执行。
- 生产密钥**不进任何测试流水线**，物理隔离（不同仓库 secrets / 不同云账号）。

## 8. 落地路线：别一上来追全自动

| 阶段 | 目标 | 人工介入 | 退出条件 |
|---|---|---|---|
| **POC（1-2 周）** | 跑通一个玩具项目的最小闭环 | 每步都看 | 能自动产出可运行的前后端 + 测试报告 |
| **试点（1-2 月）** | 一个真实中小项目，编码/评审/测试全自动 | 仅生产发布 + 最终验收 | 3 个迭代内无人工改代码 |
| **收敛（长期）** | 多项目并行 | 仅定目标 + 关键门禁 + 验收 | 交付周期稳定、缺陷逃逸率下降 |

### 度量指标（否则"更自动了"是感觉，不是事实）

| 指标 | 含义 | 目标 |
|---|---|---|
| 人工介入次数/迭代 | 越低越好 | 试点期 ≤ 3 |
| 门禁一次通过率 | 越高说明提示词与模板越成熟 | > 70% |
| 缺陷逃逸率 | staging 通过但生产出问题 | 趋近 0 |
| 返工轮次 | 平均每个 Issue 驳回次数 | < 1.5 |
| 从需求到 staging 时长 | 端到端效率 | 逐季下降 |

### 综合判断

> **架构与规范层面：满足你 90% 的需求，而且方向是对的。**
> **工程可执行层面：只有 40%，现在跑起来会"看起来成功、其实没验证"。**

**最关键的三个缺口**（不修就只是"文档很漂亮"）：

1. **`pipeline/pipeline.workflow.js` 的 `gatePass()` 恒为 `true`** —— 门禁形同虚设，任何失败都会被"通过"。这是**最危险**的问题，会让整套框架退化成角色扮演。
2. **脚本不能直接运行** —— 文件头 `export const meta` 与 DSH workflow 的脚本格式不符；且提示词是内联摘要，未读取 `prompts/` 真实模板。
3. **CI 与模板不匹配** —— `backend-check` 硬编码 Go，用 `react-python` 模板会直接红；引用的 `tests/performance/load-test.js` 不存在。

次要缺口：README 目录树漏了 `templates/` 和 `docs/02`；缺 `docs/runbook.md` 骨架；缺 Java/.NET 模板；缺 `scripts/` 统一命令契约层。
