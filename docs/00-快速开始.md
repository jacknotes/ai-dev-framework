# 快速开始：从一个新项目到 AI 接管

> 面向**使用者**。你不需要读完整套规范——**推荐的开工方式是纯对话**：在 agent 会话里说需求，其余跟着提示走。
> 想知道"为什么这样设计"，再去看 `docs/01` / `docs/03`。

---

## 0. 先回答你的两个问题

| 你的问题 | 答案 | 在哪 |
|---|---|---|
| **这个项目能当以后新项目的模板用吗？** | 能，而且已经做成一键生成。一条命令产出独立新仓库，自带 AI 手册、五道门禁、CI、隔离环境。 | §1 |
| **用户开始编程时怎么用？** | **对话式四步**（§0.1）：说需求选模板 → 新项目里问情况选档位 → 初始化 git → 说"开始"。你只在三个点介入。 | §0.1 / §2 |

### 0.1 对话式开工四步（推荐，不用读文档不用记命令）

**第 1 步｜框架仓库会话：说出你的需求**

> 「我想做一个订单管理系统，前后端分离」

AI 会对照 5 套技术栈模板推荐最适合的一套并说明理由，**你确认后**它才执行生成命令。

**第 2 步｜新项目会话：问「这是个什么项目」**

> 「当前是什么项目？用哪些智能体协同？」

项目的 AI（AGENTS.md 已注入）会介绍项目定位、技术栈、目录职责，并**推荐三档团队组合让你选**：
`quickfix`（2 个智能体，小修复） / `feature`（7 个，常规功能，默认推荐） / `full`（9 个+安全红队）。

**第 3 步｜初始化 git（必须）**

所有状态落 Git 仓库、无状态智能体靠它交接——没有 git 就没有流水线。
新项目会话检测到 `.git` 不存在时会引导你确认后执行；你确认即可。

**第 4 步｜环境就绪 → 说「开始」**

开发/测试环境定义在 `deploy/`（**强依赖**，未就绪不得开工）。
AI 会检查环境状态，经你确认后一键安装（有 Docker 走 Docker，无则本机方案）。
就绪标志：**本机浏览器能打开 http://127.0.0.1:13000（前端）**、curl 能通 http://127.0.0.1:18080（后端）——
全部服务只绑 127.0.0.1，本机可访问、局域网不可达。
四步完成后你对 AI 说「开始」，选定档位的智能体就按流水线干活了。

> 喜欢手动操作？跳过对话，直接用下面的命令也完全可以。

## 1. 创建新项目（一条命令）

```powershell
powershell -ExecutionPolicy Bypass -File tools\new-project.ps1 -Name 订单系统 -Stack react-python -Path D:\ai\订单系统
```

> 装了 PowerShell 7 的话可以把 `powershell -ExecutionPolicy Bypass -File` 简写成 `pwsh -File`。
> **Windows 自带的只有 `powershell`（5.1）**，所以下面的示例统一用 `powershell` 以保证复制即用。

| 参数 | 说明 |
|---|---|
| `-Name` | 项目名（必填） |
| `-Stack` | 技术栈，默认 `react-python`。可选：`react-python` `vue-go` `java-spring` `dotnet` `jsp-servlet` |
| `-Path` | 目标目录，省略则建在框架同级目录 |
| `-Force` | 目标目录非空时强制继续 |
| `-NoGit` | 不初始化 git |

生成的项目**完全独立**于框架仓库，改它不会影响框架。

### 生成出来的东西

```
订单系统/
├── AGENTS.md                 # ★ AI 进仓库先读这个（自动注入上下文）
├── .gitattributes            # ★ 锁定 .sh 为 LF（没有它门禁会全部失效）
├── CHANGELOG.md
├── docs/
│   ├── 00-项目约定.md         # 人看的：怎么和 AI 配合
│   ├── requirements.md       # 你写需求 + 验收标准
│   ├── architecture.md
│   ├── api-spec.yaml         # 接口契约（前后端都以此为准）
│   ├── pipeline-status.md    # 当前进度（唯一状态事实源）
│   ├── runbook.md
│   ├── test/  review/
├── frontend/  backend/       # 业务代码骨架
├── tests/                    # 集成/UI/性能（独立测试 AI 的领地）
├── scripts/                  # ★ 五入口门禁：lint build test health e2e
├── deploy/
│   ├── docker-compose.yml    # 一次性隔离环境
│   └── local/                # 无 Docker 时的本机闭环
└── .github/workflows/        # CI 门禁
```

## 2. 开始编程的标准流程

### 第 1 步：你写需求（唯一必须你亲自做的事）

编辑 `docs/requirements.md`，**验收标准必须可测**：

| ❌ 不可测 | ✅ 可测 |
|---|---|
| "登录功能要好用" | "POST /api/v1/login 正确密码返回 200 + token 字段" |
| "界面要美观" | "列表页在 1280 宽下无横向滚动条" |
| "处理异常" | "密码错误返回 401，前端显示『密码错误』" |

原因：门禁是机器判定的，**没有可测标准就无从判定**。

### 第 2 步：让 AI 开工

在项目目录里对 AI 说：

```
按 AGENTS.md 和 docs/requirements.md，实现 FR-1 健康检查接口。
```

AI 会自己读 `AGENTS.md` → 读契约 → 改对应目录 → 跑门禁。

> 你**不需要**指挥它"先建什么文件、用什么库"。说清目标和验收标准即可。
> 如果你发现它在指挥你，说明 `AGENTS.md` 被删了或没被工具加载——先把它加回来。

### 第 3 步：装依赖 + 跑门禁（首次）

```powershell
cd 订单系统

# 前端
cd frontend; npm install; cd ..

# 后端（Python 示例）
cd backend; python -m venv .venv; .venv\Scripts\activate; pip install -r requirements.txt; cd ..

# 跑门禁（Git Bash 里执行）
bash scripts/lint.sh
bash scripts/build.sh
bash scripts/test.sh
```

### 第 4 步：一键安装测试环境（先确认，再安装）

> **约定：先问用户，再装。** 安装会建虚拟环境、装依赖、起进程/容器，属于有副作用的操作。
> 读到部署方法（`deploy/README.md`）的 AI 应先向用户确认，用户同意后才执行。

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File deploy\install.ps1
```

这一条命令自动完成：探测工具链 → 选择后端（有 Docker 用 Docker，没有就本机）→ 装资源 → 启动 → 跑五道门禁。
退出码 0 = 资源就绪且门禁全绿。详见 `deploy/README.md`。

分步手动执行（不想走一键时）：

```powershell
powershell -ExecutionPolicy Bypass -File deploy\local\setup.ps1     # 一次性准备
powershell -ExecutionPolicy Bypass -File deploy\local\up.ps1        # 启动（只绑 127.0.0.1）
powershell -ExecutionPolicy Bypass -File deploy\local\verify.ps1    # 跑五道门禁，退出码即结论
powershell -ExecutionPolicy Bypass -File deploy\local\down.ps1      # 销毁，回到"从未存在"
```

> 有 Docker 时优先用 **Docker 方案**（真沙箱，`internal` 网络 + 只读根文件系统 + 资源限额）：
> ```powershell
> powershell -ExecutionPolicy Bypass -File deploy\docker\setup.ps1    # 首次：配镜像加速器 + 校验 WSL2
> powershell -ExecutionPolicy Bypass -File deploy\docker\up.ps1       # 启动
> powershell -ExecutionPolicy Bypass -File deploy\docker\verify.ps1   # 容器内跑五道门禁
> powershell -ExecutionPolicy Bypass -File deploy\docker\down.ps1     # 销毁
> ```

### 第 5 步：推 GitHub（可选）

```powershell
gh repo create 订单系统 --private --source . --push
# 或：
git remote add origin https://github.com/<你>/订单系统.git
git push -u origin main
```

然后到仓库 **Settings → Environments** 建 `staging` 和 `production`，
给 `production` 加 **Required reviewers** —— 这就是"生产发布必须你点头"的闸门。

## 3. 你只在三个点介入

| 介入点 | 时机 | 你要做什么 |
|---|---|---|
| **定目标** | 启动前 | 写需求 + 可测验收标准 |
| **关键门禁审批** | 架构评审、**生产发布前** | 批准 / 驳回 |
| **最终验收** | 门禁全绿后 | 验收交付物，发 Release |

**其余全部自动。** 但 AI 是无状态的，你随时叫停都不丢进度（状态都在 Git 里）。

## 4. 三种使用模式（按成熟度选）

| 模式 | 适用 | 人工介入 |
|---|---|---|
| **POC 验证** | 先跑通闭环 | 每步都看 |
| **试点半自动** | 编码/评审/测试全自动 | 仅生产发布 + 最终验收 |
| **收敛全自动** | 成熟项目 | 仅定目标 + 关键门禁 + 验收 |

> **强烈建议从 POC 开始**，不要一上来追全自动。

## 5. 用编排脚本跑完整闭环（进阶）

框架自带 `pipeline/pipeline.workflow.js`，用 DSH workflow 一次串起 10 个阶段。

1. 打开 `pipeline/pipeline.workflow.js`，**把全部内容**粘进 DSH 的 workflow `script`。
2. 工具的 **meta 参数**填：
   ```json
   { "name": "ai-dev-pipeline",
     "description": "AI 多智能体协同开发最小闭环",
     "phases": [{"title":"需求澄清"},{"title":"架构设计"},{"title":"任务拆解"},
                {"title":"并行编码"},{"title":"代码评审"},{"title":"集成测试"},
                {"title":"安全测试"},{"title":"部署"},{"title":"交付"}] }
   ```
3. **args 参数**填：
   ```json
   { "requirement": "你的需求", "projectRoot": "D:/ai/订单系统", "team": "feature" }
   ```
4. 运行 —— 它会调度各角色子智能体，并**真实执行 `scripts/*.sh`** 判定门禁。

### 5.1 选团队规模（`args.team`）——不必每次全部智能体一起上

| 档位 | 启用的角色 | 跳过的阶段 | 适用场景 | 大约省 |
|---|---|---|---|---|
| `quickfix` | 单开发智能体 + **轻量评审**（正确性+安全两维） | PM、架构师、任务拆解、QA、安全、部署 | bug 修复、文案、无契约变更的小改动 | ~70% |
| `feature`（默认） | PM + 架构师 + 前后端并行 + 六维评审 + QA + 部署 | 安全红队 | 常规功能开发 | 基线 |
| `full` | 全部角色 | 无 | 触碰鉴权/密码/支付/数据存储、对外接口变更、发版前 | — |

**路由规则（选档参考）：**

```
触碰鉴权/密码/支付/数据存储、对外接口、发版前  → full
涉及 docs/api-spec.yaml 的常规功能             → feature（默认）
纯 bug 修复、无契约变更的小改动                → quickfix
```

quickfix 档还支持 `args.scope`（`frontend` / `backend` / `both`，默认 `both`），限定单侧开发智能体可触碰的目录。

**三条铁律不因降档而裁剪**（任何档位都保留）：

1. 门禁必须真实退出码——quickfix 仍真实执行 lint/build/test/e2e 四道脚本；
2. 写代码的智能体不得验收自己的代码——quickfix 仍有轻量独立评审；
3. 失败退回重试——gate() 重试循环所有档位一致。

> quickfix 的运行结果带 `skippedPhases` 清单；若改动影响面超出预期（触碰契约/鉴权/存储），
> 结果的 `nextAction` 会提示改用 feature/full 重跑完整验证。

> 编排器本身**没有** shell 权限，它靠"门禁执行智能体"返回真实 `exitCode`。
> 所以门禁不可伪造——这是设计如此，不是缺陷。

## 6. 常见问题

**Q：`pwsh` 找不到 / 报"不是命令"？**
A：Windows 自带的是 `powershell`（5.1），`pwsh` 是 PowerShell 7 才有的。把命令里的 `pwsh` 换成：
```powershell
powershell -ExecutionPolicy Bypass -File <脚本路径>
```
本文档已统一用这个写法，复制即可用。

**Q：`bash` 报 `$'\r': command not found`？**
A：`.sh` 被转成了 CRLF。确认项目根有 `.gitattributes`（含 `*.sh text eol=lf`），然后：
```bash
git add --renormalize . && git checkout -- .
```

**Q：门禁红了，但看不出为什么？**
A：
```bash
bash scripts/test.sh 2>&1 | tail -40
```
脚本末行就是结论。让它把这段贴给你，而不是让它"猜哪里错了"。

**Q：能跳过 lint 先上功能吗？**
A：能，但那次提交不算"完成"。DoD 要求五道门禁全绿。

**Q：AI 非要改 `tests/` 怎么办？**
A：**拒绝**。`tests/` 是独立测试智能体的领地，开发智能体改它等于改考卷。

**Q：怎么新增一套技术栈？**
A：复制一个最接近的模板 → 只重写 `scripts/` 下的 5 个脚本 → 跑 `powershell -ExecutionPolicy Bypass -File tools\verify-framework.ps1 -Stack 你的栈`。编排器与 CI 零改动。

## 7. 框架自身怎么维护

```powershell
# 全量自检（25 个门禁脚本的语法 + 契约完整性 + 编码 + 换行符 + 吞码扫描）
powershell -ExecutionPolicy Bypass -File tools\verify-framework.ps1
```

改完任何模板/脚本后**必须**跑一遍。这是框架仓库唯一的质量底线。
